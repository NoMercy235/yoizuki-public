# Publishing Yoizuki releases

This repository contains intentionally public material only. Do not mirror a
development checkout or push its branches or tags here. A release here points
to this repository's own documentation commit; development history stays in
the corresponding development repository.

## Organization

- Put product documentation and legal files in `products/<product>/`.
- Keep each product's license and third-party notices separate.
- Use release tags `<product>-v<version>`, such as `reference-catalog-v1.0.0`.
- Attach installation archives, source snapshots when applicable, and checksums
  to releases. Do not commit archives to this repository.
- Label issues by product if more products are added.

## Release checklist

1. Build and verify the release in the product's development repository.
2. Inspect the exact source and installation archives for accidental private
   files, credentials, local paths, or unlicensed bundled content. Include the
   applicable license, notices, and required source/build materials.
3. Update this repository's product documentation and changelog. State which
   platforms were actually tested and any remaining limitations. Commit those
   public files independently of the product's development history.
4. Create a draft release against that public commit using a product-prefixed
   tag. Write release notes and attach only the reviewed, versioned artifacts.
5. Check filenames, checksums, licensing, and public links before publishing.
6. After publishing, download the assets without authentication and verify their
   checksums against the local release files.

GitHub's autogenerated source archives contain this repository's documentation.
Clearly identify the product installer and the separately attached source ZIP.
